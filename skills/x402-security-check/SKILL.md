# x402 セキュリティチェック（seller版）

コントラクト監査では見つからない部分を、seller のAPIサーバーのコードで点検する。見る相手は2つある。

- 攻撃を受けて seller が損をする場合（再送・キャッシュ・流用など）
- 攻撃がなくても buyer の代金が失われる場合（送金したのにデータが届かない）

## 範囲

git が使えるとき（Claude Code など、リポジトリの中で動いているとき）：

- 指定がなければ、main との差分（`git diff main...HEAD`）を対象にする。
- 差分が空なら「差分なし」とだけ書いて止まる。自分の判断で全体の点検に切り替えない。
- 「全体」と言われたときだけ、リポジトリ全体を対象にする。初めて点検するリポジトリでは、全体を1回回し、その後は差分だけにする。

git が使えないとき（claude.ai で「Add from GitHub」や添付でファイルを渡されたとき）：

- 渡されたファイルの全体を対象にする。差分や履歴は無いので、差分の点検はしない。
- 次のファイルが渡されていなければ、どれを追加で選べばいいかをファイル名の例で伝える。足りないまま判定できない項目は「要確認」とし、足りないファイルを理由に書く。
  - HTTPハンドラ（有料のAPIのルート）
  - x402 のミドルウェア・SDK の設定（payTo・価格・network を書いているファイル）
  - CDN・ホスティングの設定（`vercel.json`、`next.config.*`、`wrangler.toml` など）
  - lockfile（`package-lock.json`、`pnpm-lock.yaml`、`yarn.lock`、`requirements*.txt`、`poetry.lock`、`uv.lock`、`go.sum` など）

共通：

- 対象は seller のAPIサーバー側のコード（HTTPハンドラ、x402のミドルウェア設定、CDN・ホスティングの設定、依存関係）に限る。
- 対象外：USDC・JPYC等のトークンのコントラクト。buyer側のコード（ウォレットの上限、送金の確認など）。

## MCP のツール

x402-security-check の MCP のツールが使えるときは、次の項目で根拠に足す。使えないときは、コードと設定だけで判定する。

- 項目2：`inspect_402`（本番またはステージングの URL が分かる場合）
- 項目8：`get_facilitator_signers`
- 項目10：`check_sdk_advisories`（手元で動くときはリポジトリのパス、リモートのときは lockfile の中身とファイル名か、公開リポジトリの GitHub の URL を渡す）
- 項目1・3・9：`lookup_probe`（Seller Probe に購入記録があるホストの場合）
- 課題 ID の確認：`list_issues`

## 最初に確かめること

使っている x402 のミドルウェア・SDK が、どの条件で settle するかを先に読む。例えば @x402/next は、verify → ハンドラ → 応答のステータスが400未満のときだけ settle → 返す、の順で動く。この条件を基準に、「どの応答を返すと課金されるか」を各項目で判定する。

## 点検する項目

各項目について、該当するコードや設定を探し、ファイル名と行番号を根拠にして判定する。推測で判定しない。該当するコードが差分に無い項目は「対象なし」とする。

### A. 402を返すまで

1. **入力の検証を settle より先に行う**（S1）
   - リクエストのパラメータ・本文の形式、必須項目、値の範囲を、settle より前に確かめているか。不正な入力は、決済せずに 400 等を返しているか。
   - 形式は正しいが、返すデータが存在しない入力（存在しないID・コード、対象外の期間など）のとき、中身が空の成功応答を返していないか。404 等の 4xx で返していれば settle されない。
   - この項目は「決済の前に断れたか」を見る。

2. **402の中身がコード上の設定と一致する**（B6・S5・S6）
   - 入力の定義：402（またはディスカバリー用の情報）に、必要なパラメータとその形式が載っているか。
   - EIP-712 の `extra.name`・`extra.version` が、使うトークンのコントラクトのドメインと一致しているか（USDC・JPYCで異なる）。
   - 掲載価格（サイト・ドキュメント・カタログ向けの設定）と、402の `amount` が一致しているか。トークンの小数桁（USDCは6桁）で桁がずれていないか。
   - `payTo`・`asset`・`network` が、環境変数または1か所の定数から読まれているか。testnet と mainnet を取り違えていないか。

### B. 支払いを受けてデータを返すまで

3. **paymentFlow とデータを返す順序**（K1）
   - authorization と upfront のどちらを使っているかが、コードか設定で明示されているか。
   - authorization の場合：settle の成功を受けてからデータを返しているか。verify だけで返していないか。取り消せない処理（外部APIの呼び出し、外部ストアへの書き込みなど）が settle より前にないか。
   - ハンドラが失敗を 2xx（エラー本文付きの200、空の200、201など）で返す経路がないか。SDK が settle する条件に当てはまると、失敗でも課金される。
   - upfront の場合：settle 後に処理が失敗したとき、buyer にどう対応するか（再取得・返金など）がコードかドキュメントに書かれているか。
   - この項目は「失敗を成功として返していないか」を見る。項目1と同じ原因の指摘は、項目1にまとめて1件で出す。

4. **重複チェックと記録**（S7・K2）
   - 支払いIDと対象APIの組を、データを返す前にDBやKVへ一度だけ記録しているか。同じ支払いヘッダの再送で、二度データを返さないか。
   - 記録を作る条件が、SDK が settle する条件と一致しているか（例：settle は400未満で行われるのに、記録は200のときしか作らない、になっていないか）。
   - 記録の保存先が、全インスタンスで共有される場所か（サーバーレスのインスタンスごとのローカルファイルや /tmp になっていないか）。環境変数しだいで保存先が変わる場合は、本番の値を「要確認」として出す。

5. **支払いの対象と条件の一致**（S9）
   - 支払いの `resource` と、実際のリクエストのURLが一致するかを確かめているか。
   - 支払いの `accepted`（scheme・network・amount・asset・payTo）が、自分が402で提示した条件と一致するかを確かめているか。
   - 再取得の経路（支払い済みの buyer に中身を返し直す経路）でも、支払いとURLの組を確かめているか。記録が無いときに「同じ額の支払いがチェーン上にあるか」だけで返していないか。

6. **キャッシュ**（S8）
   - 有料の応答に `Cache-Control: no-store, private` が付いているか。再取得の応答だけでなく、通常の有料の応答にも付いているか。
   - CDN・ホスティングの設定で、有料のパスがキャッシュ対象から外れているか。

7. **有効期限**
   - validBefore までの残り時間を、サーバーの処理時間込みで扱っているか。SDK に任せていて自前のコードが無ければ「対象なし」。

### C. 決済の結果

8. **facilitator の結果確認**（F1・F3）
   - settle が返した tx ハッシュを、自前のRPCでもチェーン上で確かめているか。または、確かめていないことがコードかドキュメントに明示されているか。
   - `settlement_pending` のとき、ハッシュでチェーン上の確定を確かめてから再試行しているか。
   - トランザクションの送信者を、facilitator が `/supported` で公開している署名者と照合しているか。

9. **決済の応答ヘッダを返す**（F2）
   - 成功の応答に `PAYMENT-RESPONSE`（transaction・network・payer）を付けて返しているか。ブラウザから呼ばれる場合、CORS で読めるようにしているか。

### D. 依存と秘密情報

10. **SDKのバージョン**（K3）
    - 使っている x402 SDK のバージョンが、公開アドバイザリの修正版より古くないか。lockfile のバージョンを根拠にする。
    - 例：GHSA-qr2g-p6q7-w82m（Solana支払いの検証の欠陥）の修正版は @x402/svm 2.6.0、PyPI x402 2.3.0、Go 2.5.0。

11. **秘密情報**
    - 秘密鍵・APIキー・`.env` の値がコード・ログ・エラーメッセージに出ていないか。

## 重大度の基準

- Critical：支払わずに中身が取れる、または他人の資金が動く
- High：攻撃がなくても buyer の代金が失われる
- Medium：1回の支払いで、余分に中身が取れる
- Low：設定の変更など、条件がそろったときだけ起きる
- 要確認：手順や経路を書けない、または本番の設定を見ないと判定できない

## 出力

指摘ごとに次の形で書く。

```
[重大度] 項目番号（課題ID） ファイル:行
何が起きるか（悪用する手順、または buyer の代金が失われる経路を1〜2行）
誰が損をするか（seller / buyer）
直し方（1〜2行）
```

- 最初に件数（Critical n / High n / Medium n / Low n / 要確認 n）を書く。問題がなければ「指摘なし」とだけ書く。
- 問題がなかった項目は、根拠を1行ずつ書く。
- 最後に、「対象なし」とした項目の番号を1行で並べる。
- 実際に動かして確かめたことと、コードを読んで確かめただけのことを分けて書く。本番の環境変数など、見えないもので動かせなかった場合は理由を書く。
- スタイルや好みの指摘は出さない。

## 修正

- Critical と High は、修正案を作ってテストを回す。
- Medium 以下は報告だけにする。API の挙動が変わる直し方（ステータスコードの変更、経路の廃止など）は、選択肢を出して人に選んでもらう。
- 修正は自分からコミットしない。差分を示して止まる。
- フックなどがコミットを求めるときは、作業ブランチにだけコミットしてプッシュし、PR は作らない。そのことを報告に書く。
